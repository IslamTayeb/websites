## Papers worth talking about

-   *[Towards Agentic Runtime Healing](https://arxiv.org/html/2408.01055v2)* / Healer (Sun et al., arXiv 2024/2026)
    -   This is probably the cleanest "LLM as runtime-error handler" paper.
    -   The setup: program hits an unhandled runtime error, Healer grabs the error message/location/source context/runtime state, asks an LLM for a small healing snippet, executes that snippet against the current state, then resumes after the failing line.
    -   Important: it does **not** permanently patch the source code. It's runtime state repair / dynamic exception handling, not normal program repair.
        -   More concretely, their Python prototype AST-wraps candidate statements in `try/except`; on failure it prompts the LLM for replacement lines, runs the snippet via `exec()` in a copied runtime state, diffs the changed variables, merges that delta back, and continues after the failed statement.
    -   Their labels are useful: `FAIL` = still crashes, `PROCEED` = gets past the failing line, `CORRECT` = gets past the failing line and matches expected output. So `CORRECT` is a subset of `PROCEED`.
    -   Main numbers: GPT-4 gets about `73%` `PROCEED` but only about `39%` `CORRECT`; GPT-3.5 is about `48%` / `24%`; CodeQwen is about `35%` / `13%`.
    -   It seems best at local, state-recoverable errors: missing imports, undefined-but-inferable variables, type fixes, index guards, obvious attribute/name mistakes, or replacing one failing statement.
    -   It fails or becomes risky when the snippet itself errors, the needed context is missing, the bug requires broader code changes, or the execution depends on side effects / external resources / control-flow that cannot be locally reconstructed.
    -   Caveat: this is Python runtime healing, which is much friendlier than C/C++ land; segfaults, memory corruption, leaks, UB, and harder state introspection/dynamic patching are not really the same problem.
    -   The important middle category is `PROCEED` but wrong: it may skip logic, assign plausible-but-wrong defaults, mask the symptom, corrupt later state, omit returns, or replace APIs in behavior-changing ways.
    -   This supports treating runtime-error repair as a guardrail/subcase inside semantic repair, not as the whole target.
